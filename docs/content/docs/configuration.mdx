The following environment variables are available to configure Sopho for different requirements. Sopho's own variables start with `SOPHO_`; `DATABASE_URL`, `PORT` and `RUST_LOG` keep the names that hosting platforms and Rust tooling use.

## DATABASE_URL

This is used to connect to the database for running Sopho. Sopho stores data needed for its functioning in this database such as contents of cell, dashboard, canvas, authentication and so on. Do not confuse this database with [Connections](/connections). The latter are the databases and other data sources on top of which the analytics is performed using Sopho.

Sopho currently supports PostgreSQL and SQLite as options for the database. PostgreSQL is recommended for production usage. SQLite is apt for demos, exploration and hobby use cases.

The environment variable expects a database connection string as its value. For PostgreSQL, it should be in the following format:

```text
postgresql://username:password@hostname:5432/dbname
```

For SQLite, it should be in the following format:

```text
sqlite:///Users/username/database.db?mode=rwc
```

If the environment variable is not set, Sopho uses SQLite as the database by default.

## PORT

Used for setting the network port on which Sopho will run. If the environment variable is not set, it uses the port `8000` by default.

## SOPHO_FRONTEND_DIR

Path to the directory containing the frontend build, which Sopho serves at `/`. The Docker image sets it to `/app/frontend/dist/`. Sopho fails to start if it is not set, so set it when running the binary outside the image.

## SOPHO_ENVIRONMENT

Set to `development` only when developing Sopho locally: the API then accepts cross-origin browser requests, with cookies, from `http://localhost`. Any other value allows no cross-origin requests. Defaults to `production`.

## SOPHO_COOKIE_SECURE

When enabled, session cookies are marked with the Secure attribute and sent only over HTTPS. Set to `true` when serving Sopho over HTTPS (e.g. in production). Keep `false` when serving over HTTP. Defaults to `false`. See [MDN](https://developer.mozilla.org/en-US/docs/Web/Security/Practical_implementation_guides/Cookies#secure) for details.

## SOPHO_ENCRYPTION_KEY

It is used for encrypting sensitive data stored in Sopho's database such as credentials for different [Connections](/connections).

If not set, Sopho first looks for an existing key in `./data/secret.key`. If none exists, a key is generated and stored there. This is not recommended for production usage.

For production usage, provide a cryptographically secure key via the environment variable. Generate one with:

```bash
openssl rand -base64 32
```

The output of the above command can be set as the value of the environment variable.

## SOPHO_ANTHROPIC_BASE_URL

Base URL for requests to Anthropic. Leave it unset to use Anthropic's API. Set it to send requests through a proxy or a compatible endpoint; Sopho calls `<SOPHO_ANTHROPIC_BASE_URL>/v1/messages`.

## SOPHO_OPENAI_BASE_URL

Base URL for requests to OpenAI, including the version path. Leave it unset to use OpenAI's API (`https://api.openai.com/v1`). Set it to send requests through a proxy or a compatible endpoint; Sopho calls `<SOPHO_OPENAI_BASE_URL>/chat/completions`.

## RUST_LOG

Controls how much Sopho logs, using the [tracing filter syntax](https://docs.rs/tracing-subscriber/latest/tracing_subscriber/filter/struct.EnvFilter.html#directives), for example `info` or `sopho=info,tower_http=warn`. Defaults to `sopho=debug,tower_http=debug`.

## Feature flags

A feature flag turns one behaviour of Sopho on or off for the whole deployment. Each flag is an environment variable named `SOPHO_FEATURE_<NAME>` that accepts `true` or `false`. Leave it unset to keep the default. Sopho fails to start if a flag has any other value, and logs every flag at startup.

| Variable                                              | Default | Purpose                                                                                                                                                                              |
| ----------------------------------------------------- | ------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `SOPHO_FEATURE_SELF_SERVE_TENANT_CREATION`            | `false` | Lets anyone who signs in create their own tenants and become their owner, up to `SOPHO_SELF_SERVE_TENANT_LIMIT` each                                                                 |
| `SOPHO_FEATURE_PASSWORD_SIGN_IN`                      | `true`  | Lets people sign in with an email and password. When `false`, every password request is refused and people sign in only through a [Single Sign-On](#single-sign-on) provider         |
| `SOPHO_FEATURE_SEED_PASSWORD_ADMINISTRATOR`           | `true`  | Creates the administrator account from the [Admin Credentials](#admin-credentials) the first time Sopho runs                                                                         |
| `SOPHO_FEATURE_DEFAULT_TENANT`                        | `true`  | Creates the `Default` tenant with its demo data the first time Sopho runs, owned by the seeded administrator                                                                         |
| `SOPHO_FEATURE_INTERNAL_ADDRESS_CONNECTIONS`          | `true`  | Lets people connect to databases on loopback, private, link-local and other internal addresses. When `false`, a connection whose host is, or resolves to, such an address is refused |
| `SOPHO_FEATURE_BACKGROUND_SUGGESTED_QUESTION_REFRESH` | `true`  | Generates suggested questions for every connection at startup and once a day, which calls the configured AI provider. When `false`, no suggested questions are generated             |

### Combinations Sopho refuses

Some settings cannot work together. Sopho fails to start and names both settings when:

| If                                                      | Then you also need                                            | Why                                                                       |
| ------------------------------------------------------- | ------------------------------------------------------------- | ------------------------------------------------------------------------- |
| `SOPHO_FEATURE_PASSWORD_SIGN_IN` is `false`             | at least one provider in `SOPHO_OIDC_PROVIDERS`               | otherwise nobody can sign in                                              |
| `SOPHO_FEATURE_PASSWORD_SIGN_IN` is `false`             | `SOPHO_FEATURE_SEED_PASSWORD_ADMINISTRATOR` set to `false`    | the seeded administrator has only a password, so it could never sign in   |
| `SOPHO_FEATURE_SEED_PASSWORD_ADMINISTRATOR` is `false`  | at least one address in `SOPHO_PLATFORM_ADMINISTRATOR_EMAILS` | otherwise a new deployment can never have an administrator                |
| `SOPHO_PLATFORM_ADMINISTRATOR_EMAILS` is set            | at least one provider in `SOPHO_OIDC_PROVIDERS`               | a listed person becomes an administrator by signing in through a provider |
| `SOPHO_FEATURE_DEFAULT_TENANT` is `true`                | `SOPHO_FEATURE_SEED_PASSWORD_ADMINISTRATOR` set to `true`     | the default tenant and its demo are owned by the seeded administrator     |
| `SQLITE` is listed in `SOPHO_DISABLED_CONNECTION_TYPES` | `SOPHO_FEATURE_DEFAULT_TENANT` set to `false`                 | the default tenant's demo is a SQLite connection                          |

## SOPHO_SELF_SERVE_TENANT_LIMIT

How many tenants one person may create when `SOPHO_FEATURE_SELF_SERVE_TENANT_CREATION` is on. It must be a whole number of at least `1`. Defaults to `2`.

Every tenant a person has created counts. Tenants they joined by invitation, and tenants created by a platform administrator, do not count. Platform administrators create tenants without a limit.

## SOPHO_DISABLED_CONNECTION_TYPES

A comma-separated list of connection types to turn off, for example `SQLITE`. Every type is enabled unless it is listed here. The names are `POSTGRESQL`, `SUPABASE` and `SQLITE`, in capitals. Sopho fails to start if an entry is not a connection type or appears twice.

A type that is turned off is not offered when creating a connection. Connections of that type that already exist stay listed and are marked unavailable. They cannot be queried or changed.

A SQLite connection reads a file on the server that runs Sopho, so turn `SQLITE` off on a deployment that people outside your organisation can sign in to.

## Internal addresses

When `SOPHO_FEATURE_INTERNAL_ADDRESS_CONNECTIONS` is `false`, Sopho refuses a PostgreSQL or Supabase connection whose host is, or resolves to, a loopback, private, link-local, carrier-grade NAT or unspecified address, including the IPv6 equivalents. A host name that does not resolve is refused too. The check runs when a connection is created, changed or first used.

This check gives people a clear error. It is not a complete guard: the host is checked when Sopho first opens a connection to it, and a host name can resolve to a different address later. On a public deployment, also block outbound traffic from Sopho to internal ranges and the cloud metadata address with a firewall.

## Connection credentials

Sopho passes a PostgreSQL or Supabase connection's host, port, username, password and database to the driver exactly as typed. Special characters such as `@`, `/` and `#` need no escaping.

Earlier versions joined these fields into a URL. If you percent-encoded a value to make it work, for example `p%40ss` for `p@ss`, or added options after the database name, such as `sales?sslmode=require`, edit the connection and enter the plain value.

## Response headers

Sopho adds these headers to every response:

| Header                    | Value                             |
| ------------------------- | --------------------------------- |
| `X-Content-Type-Options`  | `nosniff`                         |
| `Referrer-Policy`         | `strict-origin-when-cross-origin` |
| `Content-Security-Policy` | `frame-ancestors 'none'`          |
| `X-Frame-Options`         | `DENY`                            |

Sopho cannot be embedded in a frame on another site. Set `Strict-Transport-Security` on the proxy that serves HTTPS in front of Sopho.

## SOPHO_PLATFORM_ADMINISTRATOR_EMAILS

A comma-separated list of email addresses, for example `ada@example.com,grace@example.com`. A listed person becomes a platform administrator when they sign in through a [Single Sign-On](#single-sign-on) provider that confirms that email address. Leave it unset or empty for an empty list. Sopho fails to start if an entry is blank, is not an email address, or appears twice.

The list only promotes. Signing in with a password never promotes, and nothing happens at startup or when the list changes. A listed person who is demoted in the UI becomes an administrator again at their next sign-in, so remove them from the list as well.

## Admin Credentials

The first time Sopho runs, the following four environment variables are used to seed the initial admin user so you can log in after bootup. The application fails to start if any of these are not set. When `SOPHO_FEATURE_SEED_PASSWORD_ADMINISTRATOR` is `false`, they are not read and no account is seeded; an administrator seeded on an earlier start is left as it is.

| Variable                | Purpose                                                 |
| ----------------------- | ------------------------------------------------------- |
| `SOPHO_ADMIN_USERNAME`  | Login username for the admin account                    |
| `SOPHO_ADMIN_PASSWORD`  | Password for the admin account                          |
| `SOPHO_ADMIN_EMAIL`     | Email used to identify the admin and enforce uniqueness |
| `SOPHO_ADMIN_FULL_NAME` | Display name for the admin user                         |

Use a strong password in production.

## Single Sign-On

People can sign in through any OpenID Connect provider, such as Google, Microsoft Entra ID or Okta. Without a provider, people sign in with a password. Inviting people to a tenant needs a provider or [email](#email).

`SOPHO_OIDC_PROVIDERS` lists the providers, separated by commas, for example `google,okta`. A name may contain letters, digits and dashes. Each provider then needs the following five variables, where `<NAME>` is the provider name in upper case with dashes turned into underscores (`my-idp` becomes `MY_IDP`). Sopho fails to start if any of them is missing.

| Variable                          | Purpose                                                                                               |
| --------------------------------- | ----------------------------------------------------------------------------------------------------- |
| `SOPHO_OIDC_<NAME>_DISPLAY_NAME`  | Label of the sign-in button, for example `Google`                                                     |
| `SOPHO_OIDC_<NAME>_ISSUER_URL`    | The provider's issuer URL. Sopho reads its settings from `<issuer>/.well-known/openid-configuration`  |
| `SOPHO_OIDC_<NAME>_CLIENT_ID`     | Client ID of the application registered with the provider                                             |
| `SOPHO_OIDC_<NAME>_CLIENT_SECRET` | Client secret of that application                                                                     |
| `SOPHO_OIDC_<NAME>_REDIRECT_URI`  | `https://<your Sopho host>/api/v1/auth/oidc/<name>/callback`. Register the same URI with the provider |

Sopho asks for the `openid`, `email` and `profile` scopes. The provider must return the person's email, marked as verified, and their name. Someone signing in for the first time gets an account without a tenant and joins tenants by accepting invitations. Signing in through a provider that confirms the email of an existing account adds the provider to that account, once the account's email has been proven by an emailed link or another provider. The admin created at startup has not proven its email: it signs in with its password and connects a provider from its profile.

### Running without passwords

To accept sign-in only through a provider, set `SOPHO_FEATURE_PASSWORD_SIGN_IN`, `SOPHO_FEATURE_SEED_PASSWORD_ADMINISTRATOR` and `SOPHO_FEATURE_DEFAULT_TENANT` to `false`, configure a provider, and name at least one administrator in `SOPHO_PLATFORM_ADMINISTRATOR_EMAILS`. A new deployment then starts with no accounts and no tenants. The first listed person to sign in becomes a platform administrator. Turn on `SOPHO_FEATURE_SELF_SERVE_TENANT_CREATION` so people can create their own tenant.

With passwords off, the sign-in page shows only the provider buttons, and the password pages and controls are not shown. Stored passwords are kept and work again if you turn the flag back on. People who are already signed in stay signed in.

Before turning passwords off on a deployment that already has accounts:

1. Configure the provider and add the administrator emails.
2. Make sure every account can sign in through the provider. An account created from an emailed invitation links to the provider at its first provider sign-in. The seeded administrator has not proven its email, so that person must sign in with the password and connect the provider from their profile first.
3. Set `SOPHO_FEATURE_SEED_PASSWORD_ADMINISTRATOR` and `SOPHO_FEATURE_DEFAULT_TENANT` to `false`. The existing administrator account and default tenant stay as they are.
4. Set `SOPHO_FEATURE_PASSWORD_SIGN_IN` to `false`.

An account that skipped step 2 cannot sign in until you turn password sign-in back on, and is told to contact its administrator. Two cases cannot be fixed from inside Sopho:

- A seeded administrator whose `SOPHO_ADMIN_EMAIL` is not a real address at the provider can never connect it. Appoint another owner for the default tenant and name a real administrator in the list before you switch.
- A person invited at an address that has no account with the provider cannot join.

For example, for Google:

```bash
SOPHO_OIDC_PROVIDERS=google
SOPHO_OIDC_GOOGLE_DISPLAY_NAME=Google
SOPHO_OIDC_GOOGLE_ISSUER_URL=https://accounts.google.com
SOPHO_OIDC_GOOGLE_CLIENT_ID=<client id>
SOPHO_OIDC_GOOGLE_CLIENT_SECRET=<client secret>
SOPHO_OIDC_GOOGLE_REDIRECT_URI=https://sopho.example.com/api/v1/auth/oidc/google/callback
```

## Email

Sopho sends email to invite people, to reset forgotten passwords, and to tell people when the way they sign in changes. Email is on when `SOPHO_SMTP_HOST` is set. Sopho then needs the other settings below, and fails to start if one is missing or invalid.

| Variable              | Purpose                                                                                                               |
| --------------------- | --------------------------------------------------------------------------------------------------------------------- |
| `SOPHO_SMTP_HOST`     | Host of the mail server                                                                                               |
| `SOPHO_SMTP_PORT`     | Port of the mail server, usually `587` or `465`                                                                       |
| `SOPHO_SMTP_TLS`      | `starttls` (usually port 587), `tls` (usually port 465), or `none` for a local test server only                       |
| `SOPHO_SMTP_USERNAME` | User name for the mail server. Set it together with the password, or leave both unset                                 |
| `SOPHO_SMTP_PASSWORD` | Password for the mail server                                                                                          |
| `SOPHO_EMAIL_FROM`    | Sender of every email, for example `Sopho <no-reply@example.com>`                                                     |
| `SOPHO_PUBLIC_URL`    | The address people use to reach Sopho, for example `https://sopho.example.com`. Every link in an email starts with it |

Emails wait in a queue in Sopho's database and are retried when the mail server can't take them, so a short outage delays emails instead of losing them. Platform administrators see every email and its status on the Emails page.

For example:

```bash
SOPHO_SMTP_HOST=smtp.example.com
SOPHO_SMTP_PORT=587
SOPHO_SMTP_TLS=starttls
SOPHO_SMTP_USERNAME=<user name>
SOPHO_SMTP_PASSWORD=<password>
SOPHO_EMAIL_FROM="Sopho <no-reply@example.com>"
SOPHO_PUBLIC_URL=https://sopho.example.com
```
